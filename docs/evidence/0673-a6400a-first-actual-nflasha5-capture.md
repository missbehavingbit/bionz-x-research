`usbstor.inf`, version `10.0.26100.9818`, healthy at the saved physical port.
The existing allowlisted native inquiry/model-info tool runs in an
owner-approved elevated process. It sends its model request once; one explicit
BUSY response is followed by a response-only read, not request replay.

The native response passes:

- Model `ILCE-6400A`, product-code bytes `0032858730`.
- Transaction elapsed **0.204896 seconds**, including the BUSY read delay.
- No updater initialization, mode switch, sector I/O, driver change or

firmware version**. The owner's separate `1.01` confirmation is the version

## 4. Failed handoff, then immediate acquisition

First entry authenticates successfully and observes healthy `054C:0336` at
`18:28:49.314595Z`. A separately launched acquisition starts at `18:30:10Z`
and instead observes **`054C:0994` / HidUsb**.

That client:

- Stops at device admission.
- Sends **no START/authentication/data request**.
- Creates no one-shot data-request marker or partition capture.
- Does not touch the `0994` driver.

The cause of the identity change during the approximately 81-second handoff
gap is **unmeasured**. It is not automatically attributed to an idle timeout,
reboot, handle close, successful STOP or owner power-switch action.

The owner reports that the physical switch was ON, then performs an ordinary
restart and returns to Mass Storage. Normal WinUSB/port/receipt admission is
checked again. A new, explicitly chained entry and acquisition runs
back-to-back, with no idle handoff:

1. One new normal-mode START/authentication entry.
2. Verify healthy `0336`.
3. Immediately start the guarded client.
4. Reauthenticate on the admitted service handle.
5. One literal fixed-node request, actual acknowledged length **16**.
6. Validate all response frames and save the complete 60 MiB.
7. Flush/fsync, verify the host file and preserve the one-shot marker.
8. Attempt one explicit STOP and observe normal USB.

This is not a repeated partition request: the first client stopped before
sending one. The successful baseline's persistent marker is retained; do not
delete it to replay a request.

## 5. Exit and recovery boundary

All data bytes and terminators complete. STOP returns the declared PIPE
behavior, which is not an acknowledgment. The client therefore preserves a
valid capture but does **not** return clean-recovery success.

The owner reports the screen **“Check the connected device”**. A later
host-only observation confirms healthy normal `054C:0F0F` / WinUSB at the same
port, not Senser. That screen alone neither invalidates the dump nor proves
firmware resources were released. WinUSB is not the normal Windows storage
class driver.

The requested post-capture ordinary OFF/ON restart is not inferred from that
screen. The owner is guided to restore only `054C:0F0F` to Microsoft USB Mass
Storage / USBSTOR using Device Manager, leaving `0336` and `0994` unchanged.
Postflight remains pending until actual observations establish its outcome.
No further camera protocol request is sent while that recovery is uncertain.
No `/proc/uptime`, debugger or `/tmp_bt` observation is fabricated.

A tightly coupled reporting correction follows: unexpected non-normal
identities such as `0994` now require attention even when the rejected client
itself sent no command. The first failed receipt's old
`recovery_required=false` field is preserved, not reinterpreted as a clean
camera. Its `cleanup_verified=false` and empty event list remain authoritative.
A constructed regression covers unexpected HID and normal pre-entry refusal.
